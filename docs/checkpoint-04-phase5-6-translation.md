# 체크포인트 04 — Phase 5·6 완료: 번역 연동 + 자막 출력 (2026-09-23)

## 이 시점까지 만든 것

- `translation.TranslationClient` 인터페이스 + `PapagoTranslationClient` 구현체
- `/setoutputlang` 커맨드 + `UserOutputLanguageRegistry` (화자가 "내 발화를 번역해서 보여줄 언어"를 설정)
- `UserAudioReceiveHandler`가 STT 결과를 받으면 곧바로 Papago로 번역하고, 그 결과를 봇이 접속한 음성 채널의 텍스트 채팅에 자막으로 올림
- 실제 디스코드 테스트로 한국어 발화 → 영어/일본어 자막까지 확인 완료

이걸로 **Phase 5(번역 연동)와 Phase 6(결과 출력)이 끝났다.**

## 설계 실수 — "누가 언어를 설정하는가"를 잘못 짚었던 순간

`/setoutputlang`을 처음 설계할 때, **리스너(청자) 각자가 자기가 알아듣고 싶은 언어를 설정**하는 구조로 착각하고 구현을 시작했다. 그 가정대로 가면 봇이 번역 결과를 보여줄 때마다 "지금 이 음성 채널에 누가 있는지" 전부 조회하고, 그 사람들이 각자 설정한 언어의 합집합만큼 번역을 여러 번 돌려야 한다 - 채널 멤버 목록 조회, 멤버별 언어 다중 관리, 발화 하나당 번역 API 호출 N번(N=서로 다른 언어를 원하는 청자 수)까지 필요해지는 훨씬 복잡한 구조였다.

실제로는 정반대였다. **화자 본인이 "내가 말할 언어(`/setlang`)"와 "그 말을 번역해서 보여줄 언어(`/setoutputlang`)"를 둘 다 설정한다.** 즉 한 발화당 번역은 항상 정확히 한 번만 일어난다. 청자가 여러 언어를 쓰더라도 봇은 화자가 정해준 한 가지 타겟 언어로만 자막을 올린다.

이 정정 덕분에:
- `UserOutputLanguageRegistry`는 `UserLanguageRegistry`와 완전히 같은 모양(유저 ID → 언어, 기본값 KO)으로 단순하게 끝났다.
- 채널 멤버를 조회하거나 순회할 필요가 아예 없어졌다.
- 번역 API 호출 횟수가 발화당 최대 1번으로 고정된다 (뒤에 나올 비용 이야기에서 중요해짐).

**교훈**: "누구를 위한 기능인가"를 잘못 짚으면 구현 복잡도가 완전히 다른 방향으로 커진다. 코드를 쓰기 전에 "이 값을 누가 정하고, 누구 기준으로 조회되는가"부터 명확히 하고 시작해야 한다.

## 부수적으로 따라온 UX 디테일 — "화자는 자기가 설정한 출력 언어를 모른다"

`/setoutputlang`으로 설정을 마치면 봇이 확인 메시지를 보여주는데, 처음엔 방금 고른 언어(outputLanguage)로 그 메시지를 띄웠다. 그런데 outputLanguage는 정의상 "화자 본인이 못 알아듣는 청자를 위한 언어"다 - 화자가 영어를 모르는데 `/setoutputlang EN`을 했다면, 그 확인 메시지를 영어로 띄우는 순간 화자는 설정이 제대로 됐는지조차 읽을 수 없다.

그래서 `/setoutputlang`의 모든 응답(성공/실패 둘 다)은 outputLanguage가 아니라 **화자의 spokenLanguage(`/setlang`으로 설정한 값)** 로 보여주도록 고쳤다. 같은 이유로, 화자의 현재 spoken language와 같은 언어를 outputLanguage로 선택하려 하면(번역해도 항상 원문 그대로 나오는 무의미한 설정) 거부하는데, 이 검증도 실행 시점에 한다 - 디스코드 슬래시 커맨드의 choice 목록은 유저별로 동적으로 못 바꾸기 때문이다.

## 자막을 어디에 올릴 것인가 — 별도 채널 설정 없이 해결됨

Phase 6을 시작할 때 "번역 결과를 어느 채널에 보여줄까"를 고민했는데, JDA를 까보니 이미 해결책이 있었다. 디스코드가 음성 채널 자체에 텍스트 채팅 기능을 추가한 이후, JDA의 `VoiceChannel`과 `StageChannel` 둘 다 `GuildMessageChannel`을 구현한다:

```
VoiceChannel extends ... GuildMessageChannel ...
StageChannel extends ... GuildMessageChannel ...
AudioChannelUnion.asGuildMessageChannel()  // 어느 쪽이든 안전하게 메시지 채널로 변환
```

덕분에 "번역 결과를 저장할 채널 ID를 어딘가 설정해두고 관리"하는 기능 자체가 필요 없어졌다. 봇이 접속한 바로 그 음성 채널에 `voiceChannel.asGuildMessageChannel().sendMessage(...)`로 바로 보내면 되고, 통화 중인 사람들이 보고 있을 확률이 가장 높은 위치이기도 하다.

메시지 형식은 `**서버 별명**: 원문` 다음 줄에 번역문을 붙이는 형태로 정했다. 번역문만 보여주면, 원문 언어를 아는 사람이 오역을 발견해도 확인할 방법이 없어서 원문을 같이 남긴다.

## 별명 표시 — `User.getName()`이 아니라 `Member.getEffectiveName()`

자막에 화자 이름을 넣을 때 `User.getName()`(디스코드 계정의 전역 유저네임)을 그대로 썼더니, 실제 서버에서 부르는 별명과 다르게 나왔다. `Guild.getMember(user).getEffectiveName()`으로 바꿔서 서버 별명(없으면 글로벌 이름으로 자동 대체)을 쓰도록 고쳤다. `MemberCachePolicy.VOICE`를 이미 켜둔 덕분에 방금 말한 화자는 항상 멤버 캐시에 있어서 정상적으로는 항상 별명을 찾을 수 있지만, 혹시 캐시 미스가 나면 `User.getName()`으로 안전하게 대체하도록 방어했다.

## 실측 지연 시간

Phase 6까지 끝난 시점에 실제 파이프라인 지연을 추정해봤다 (정밀 계측은 아직 없음).

| 구간 | 지연 | 근거 |
|---|---|---|
| 발화 종료 → 무음 감지 | 800~1000ms | `SILENCE_THRESHOLD_MILLIS`(800) + 200ms 폴링 주기, 파이프라인에서 가장 큰 고정 비용 |
| STT (CLOVA/Azure) | 실측 안 됨, 수백ms~1~2초 추정 | 문장이 길수록 늘어남 |
| Papago 번역 | **228ms (실측)** | 로그 타임스탬프로 직접 측정 |
| 텍스트 채널 전송 | 100~300ms | JDA `sendMessage().queue()`의 디스코드 API 왕복 |

합쳐서 대략 1.5~3초 정도로, "동시통역"보다는 "약간 딜레이 있는 자막"에 가깝다. 사용자가 이 정도 지연은 감수하기로 결정해서 스트리밍 전환 없이 발화 단위 전송을 계속 유지하기로 했다.
